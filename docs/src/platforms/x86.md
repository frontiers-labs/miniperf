# Linux on x86-64

miniperf detects the CPU from `cpuid` and loads a curated event table when it has one. Other x86-64 CPUs get the portable events and the architectural top-down fallback.

## Intel

**Tiger Lake** (models 0x8c and 0x8d) ships with 231 core events generated from Linux perf's event data and a two-level top-down scenario. Architectural counters the part does not support are dropped with a notice instead of aborting the run.

**Ice Lake and newer** expose `PERF_METRICS`. The `tma` scenario and `mperf stat --topdown` use it for exact level-1 metrics, and level 2 on Sapphire Rapids and newer. Hybrid parts with an `cpu_atom` PMU are excluded from the fixed path and use counter formulas.

**PEBS** provides precise memory samples with data address and latency on any core whose PMU reports `max_precise` of 2 or more and exposes the `mem-loads` and `mem-stores` aliases. Kernel 5.12 or newer is required for latency. miniperf raises the load-latency threshold to 30 cycles so the sample stream is not flooded with L1 hits.

**LBR call stacks** are requested first on Intel. If the PMU has no call-stack mode, recording falls back to DWARF unwinding automatically.

**Memory bandwidth** comes from the `uncore_imc` PMUs when system-wide events are allowed. That needs `kernel.perf_event_paranoid` at 0 or lower, or `CAP_PERFMON`.

## AMD

Every Zen generation has a core event table generated from Linux perf's event data. miniperf picks the table from the CPUID family and model, with the same model ranges as perf's `mapfile.csv`:

| Table | Family, models | Core events | Top-down |
|---|---|---|---|
| `zen1` (Zen, Zen+) | 17h, 00h to 2Fh | 163 | Stall counters, two levels |
| `zen2` | 17h, 30h and up | 199 | Stall counters, two levels |
| `zen3` | 19h, 00h to 0Fh, 20h to 2Fh, 40h to 5Fh | 223 | Stall counters, two levels |
| `zen4` | 19h, other models | 337 | Dispatch slots, two levels |
| `zen5` | 1Ah, 00h to 2Fh, 40h to 4Fh, 60h to 7Fh | 363 | Dispatch slots, two levels |
| `zen6` | 1Ah, other models | 425 | Dispatch slots, two levels |

The tables hold core PMU events only. L3, data-fabric, and memory-controller events belong to the `amd_l3`, `amd_df`, and `amd_umc` PMUs and are not listed.

**Top-down on Zen 4 and newer** uses the dispatch-slot events (`de_no_dispatch_per_slot`), the same events and formulas as perf's `PipelineL1` and `PipelineL2` metric groups. A slot is one of 6 dispatch positions per cycle on Zen 4 and one of 8 on Zen 5 and Zen 6. Level 1 has the four usual buckets plus `smt_contention`, the slots given to the sibling hardware thread. Level 2 splits each bucket in two:

| Level 1 | Level 2 |
|---|---|
| `retiring` | `fastpath`, `microcode` |
| `bad_speculation` | `branch_mispredict`, `pipeline_restarts` |
| `fe_bound` | `fetch_latency`, `fetch_bandwidth` |
| `be_bound` | `memory_bound`, `core_bound` |

The rung is `amd_dispatch_slots`. The model needs 11 events and Zen has 6 counters, so the kernel rotates three or four counter groups and each metric comes from the share of the run its group was scheduled for. The rung reports `scaled` quality for that reason. Run the workload long enough for every group to get a fair share, a second or more.

**Top-down on Zen, Zen+, Zen 2, and Zen 3** has no slot events to use. Level 1 is fractions of cycles from the fetch-stall counters, and the backend splits on L2 fill activity. The stall counters saturate, so the buckets can exceed 1 in sum. See the caveats in [Top-down microarchitecture analysis](../concepts/topdown.md).

**IBS**, AMD's precise sampling, fills the same `mem_samples` tables as PEBS through the `ibs_op` PMU. IBS tags every retired op and the driver keeps the loads and stores. The sample period therefore counts ops, not loads, and the rung reports `estimated` quality. IBS has no hardware privilege filter, so miniperf needs the kernel's software filter, the `swfilt` format of the `ibs_op` PMU, to sample user space only. `mperf doctor` reports a kernel without it. The IBS PMU accepts no branch-stack request, so IBS samples carry the kernel callchain and a stack dump for DWARF unwinding, not branch records.

**Branch records.** Zen 3 and newer expose a branch buffer that records all branches. miniperf replays it to reconstruct call stacks. Older Zen has none, and DWARF unwinding is used.

**Memory bandwidth** comes from the `amd_df` or `amd_umc` PMUs, with the same permission requirement as Intel.

## Virtual machines

Most hypervisors do not expose the PMU. `mperf doctor` reports `cpu-cycles cannot be opened` as a blocker, and `mperf stat` prints a notice. Software counters still work. Some hypervisors pass the core PMU through but not uncore or PEBS. The fidelity line and `snapshot_collectors` say what was available.
